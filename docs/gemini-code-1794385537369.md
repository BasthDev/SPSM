# 📚 Blueprint & Arsitektur Terintegrasi: SPSM v2.0
**(Sarana Pengajuan Skripsi Mahasiswa)**

Dokumen ini merupakan pedoman arsitektur dan alur kerja (workflow) terpusat untuk sistem SPSM v2.0. Sistem ini mendigitalkan seluruh proses pengajuan judul skripsi, pemilihan Dosen Pembimbing, hingga penerbitan Surat Keputusan (SK) secara otomatis menggunakan ekosistem **Expo React Native** (Mobile), **React JS** (Web Portal), dan **Appwrite** (Backend-as-a-Service).

---

## 1. Manajemen Masa Pengajuan & Akses (Admin & System)

Admin mengendalikan penuh jadwal pengajuan melalui *database* terpusat.
* **Tabel Pengaturan (`system_settings`)**: Berisi `is_active` (boolean), `start_date`, `end_date`, dan `academic_year`.
* **Validasi Mobile**: Saat aplikasi mahasiswa dibuka, sistem mengecek tanggal server. Jika di luar jadwal, tombol *Submit* terkunci dan muncul *banner* peringatan.
* **Pengecualian Sistem (*Bypass*)**: Mahasiswa yang memiliki riwayat pengajuan dengan status `revision` atau `rejected` memiliki hak istimewa untuk mengabaikan blokir jadwal ini agar tetap dapat mengirimkan revisi judulnya kapan saja.

---

## 2. Autentikasi & Onboarding (Google OAuth)

Autentikasi diwajibkan menggunakan akun Google (SSO) agar cepat dan aman.
1. **Login**: Mahasiswa menekan "Masuk dengan Google" memicu `account.createOAuth2Session()` dari Appwrite.
2. **Pengecekan Profil**: Sistem memvalidasi apakah `user_id` sudah ada di koleksi `users`.
3. **Onboarding**: Jika belum ada (pengguna baru), mahasiswa diwajibkan mengisi:
   * NIM (Nomor Induk Mahasiswa)
   * Nama Lengkap (Otomatis dari Google, dapat diedit)
   * Program Studi (Dropdown)
   * Tahun Angkatan
   * Nomor WhatsApp (Opsional)

---

## 3. Alur Kerja Sistem (End-to-End Workflow)

Proses ini berjalan linier dari mahasiswa hingga penerbitan surat resmi.

### Fase 1: Validasi & Input Pengajuan (Aktor: Mahasiswa)
1. **Cek Syarat Akademik**: Sistem memastikan mahasiswa telah lulus >110 SKS dan mata kuliah Metodologi Penelitian.
2. **Pengisian 3 Opsi Judul**: Mahasiswa wajib menginput 3 alternatif judul. Masing-masing judul harus memiliki:
   * Teks Judul
   * Latar Belakang Masalah
   * Referensi Jurnal (File PDF - Opsional)
   * **Tabel Relevansi**: Terdiri dari (1) Fokus/Variabel, (2) Metodologi, dan (3) Kesesuaian jurnal dengan topik.
3. **Plotting Awal Pembimbing**: Mahasiswa memilih 2 calon Dosen Pembimbing (Prioritas 1 dan 2).
4. **Submit**: Data dikirim, status berubah menjadi `pending_lecturer`.

### Fase 2: Evaluasi & Plotting Dosen (Aktor: Dosen Reviewer)
1. **Review Komprehensif**: Reviewer memeriksa ketiga opsi judul beserta tabel relevansinya via *Web Dashboard*.
2. **Hak Plotting**: Reviewer berhak **menetapkan atau mengubah** 2 Dosen Pembimbing secara sepihak, terlepas dari prioritas yang dipilih mahasiswa.
3. **Keputusan Tolak (Reject/Revision)**: 
   * Jika tidak ada yang layak, reviewer menekan tombol **Tolak/Revisi**.
   * Ketiga judul otomatis ditandai `rejected` dan WAJIB diberikan catatan spesifik (misal: *"Judul 1: Metodologi salah"*).
   * Mahasiswa melihat catatan secara transparan di aplikasi dan diminta mengajukan ulang.
4. **Keputusan Terima (Approve)**:
   * Reviewer memilih **1 judul terbaik** dan meneruskan pengajuan. Status berubah menjadi `waiting_kaprodi`.

### Fase 3: Pleno & Pengesahan (Aktor: Kaprodi)
1. **Agregasi Data**: Dashboard Kaprodi HANYA menampilkan data berstatus `waiting_kaprodi`. Pengajuan yang ditolak/revisi tidak masuk hitungan antrean.
2. **Verifikasi Akhir**: Kaprodi mengecek similaritas judul dan menyetujui (atau mengubah) 2 Dosen Pembimbing final.
3. **Pengesahan**: Kaprodi menekan tombol **Sahkan (Approve)**. Status berubah menjadi `approved` / `verified`.

### Fase 4: Automasi SK & Penomoran Surat (Sistem Backend)
Berjalan otomatis sedetik setelah Kaprodi melakukan *Approve*:
1. **Generate Nomor Surat**: Dibuat berformat `URUTAN/SPSM/PRODI/ANGKATAN/TAHUN` (Contoh: `01/SPSM/BD/23/2026`).
2. **Logika Urutan**: *Increment* otomatis berdasarkan data yang disetujui, dan di-*reset* setiap pergantian tahun.
3. **Generate No. Dokumen**: Membuat *Unique ID* permanen (Contoh: `SPSM-6AF2DC410034D8AC2BDA`) untuk validasi *cross-platform*.
4. **Penyimpanan**: Sistem mencatat hasil ke dalam tabel `surat` di Appwrite Database. File *template* SK juga disiapkan.

### Fase 5: Distribusi SK (Aktor: Sistem -> Mahasiswa)
1. **Notifikasi**: Mahasiswa menerima *push notification* bahwa judul telah disahkan.
2. **Unduh SK**: Pada halaman detail aplikasi, muncul tombol **"Download SK"**. Mahasiswa dapat mengunduh *file* PDF/Word resmi yang sudah berisi Nomor Surat dan No. Dokumen, siap digunakan untuk mulai bimbingan.

## 4. Struktur Database Appwrite

Konfigurasi koleksi (*collections*) pada database `spsm_db`:

### 1. `users` (Data Pengguna)
| Atribut | Tipe | Keterangan |
| :--- | :--- | :--- |
| `user_id` | String | ID Auth Appwrite |
| `name` | String | Nama Mahasiswa / Dosen |
| `role` | String | `student`, `lecturer`, `kaprodi`, `admin` |
| `nim_or_nip` | String | NIM / NIP |
| `department` | String | Program Studi |
| `batch_year` | Integer | Tahun Angkatan |

### 2. `thesis_submissions` (Header Pengajuan)
| Atribut | Tipe | Keterangan |
| :--- | :--- | :--- |
| `student_id` | String | Relasi ke `users` |
| `advisor_1_id` | String | Dosen Pembimbing 1 (Bisa Null saat draft) |
| `advisor_2_id` | String | Dosen Pembimbing 2 (Bisa Null saat draft) |
| `status` | String | `drafting`, `pending_lecturer`, `waiting_kaprodi`, `approved`, `revision`, `rejected` |
| `submitted_at` | Datetime | Waktu pengajuan |

### 3. `submission_options` (Detail 3 Opsi Judul)
| Atribut | Tipe | Keterangan |
| :--- | :--- | :--- |
| `submission_id` | String | Relasi ke `thesis_submissions` |
| `option_number` | Integer | Urutan judul (1, 2, atau 3) |
| `title` | String | Teks judul skripsi |
| `background` | Text | Latar belakang masalah |
| `journal_file_id`| String | ID File PDF Referensi (Null jika tidak ada) |
| `relevance_table`| Text | JSON/String berisi matriks tabel relevansi |
| `lecturer_notes` | Text | Catatan revisi dari dosen reviewer per judul |
| `is_selected` | Boolean | True jika judul ini yang dipilih dosen |

### 4. `surat` (Automasi Dokumen SK)
| Atribut | Tipe | Keterangan |
| :--- | :--- | :--- |
| `submission_id` | String | Relasi ke `thesis_submissions` |
| `nomor_surat` | String | Format: URUTAN/SPSM/PRODI/ANGKATAN/TAHUN |
| `urutan` | Integer | Angka *increment* (Otomatis reset tahunan) |
| `no_dokumen` | String | Unique Identifier (SPSM-XXXXXX) |
| `file_sk_id` | String | ID File Template SK (PDF/Word) |
| `issued_at` | Datetime | Waktu surat digenerate |

### 5. `system_settings` (Pengaturan Admin)
| Atribut | Tipe | Keterangan |
| :--- | :--- | :--- |
| `is_active` | Boolean | Status pembukaan pengajuan |
| `start_date` | Datetime | Waktu mulai |
| `end_date` | Datetime | Waktu tutup |
| `academic_year` | String | Contoh: 2025/2026 Ganjil |

## 5. Standardisasi State Management (Status Enum)

Pemetaan status ini sangat penting di-*handle* oleh *frontend* (React Native / React JS) untuk menampilkan/menyembunyikan tombol UI:
1. **`drafting`**: Menyusun 3 judul & tabel relevansi.
2. **`pending_lecturer`**: Terkirim, menanti evaluasi Reviewer.
3. **`revision` / `rejected`**: Ditolak. Membaca catatan per judul, bersiap kirim ulang.
4. **`waiting_kaprodi`**: Judul di-ACC Reviewer, menunggu ketuk palu Kaprodi.
5. **`approved`**: Sah. Tombol *Download SK* muncul, Nomor Surat tergenerate.

│   └── submissionService.js # Logika Insert 3 Judul, Upload PDF & Ambil SK
